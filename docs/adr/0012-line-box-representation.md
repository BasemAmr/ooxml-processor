# 0012 — Line Box representation: multi-segment lines, visual cluster storage, and source back-references

**Status:** Accepted

## Context

The Line Box is the single most-depended-on data structure in the system. It is generated by the line breaker (P5-01) and used directly for:

- Caret placement and mapping between logical source offsets and physical coordinates
- Hit-testing (clicking to place the cursor)
- Selection geometry (drawing the blue highlight over selected text)
- Float exclusions (P9-05, splitting text around floating images)
- Incremental relayout (P6-13, identifying which lines need to be recomputed when text changes)

If the structure of the line box is wrong, fixing it later means simultaneously touching everything from Phase 6 through Phase 9. We need to lock in three key constraints now, even though they will only be heavily exercised in later phases.

## Decision

We have locked down the Line Box representation using three primary architectural choices:

### 1. Multi-segment lines

A line is defined as a collection of `segments: Segment[]` with length >= 1.
Because of float exclusions (P9-05) and drop caps (P5-12), a single visual "line" of text may actually be broken into multiple horizontal intervals, stepping over floating objects. Designing with segments from day one prevents a massive refactoring later. Operations like hit-testing or offset mapping must always account for multi-segment layouts.

### 2. Visual order vs logical source back-references

Clusters within a segment are strictly in **visual order** (screen left to right). This allows painters and hit-testers to iterate sequentially without branching on text direction.
However, each visual cluster carries its logical `srcOffset` and `srcLength` back into the source `w:r` node (using `NodeId`).

- `srcOffset` is **not** monotonic across RTL segments (the left-most cluster on screen has the highest logical offset).
- The pairs of `srcOffset`/`srcLength` completely tile the source text for the segment with no gaps and no overlaps, ensuring robust mapping in both directions.

### 3. Flat numeric cluster storage (Shared with P4-12)

A 500-page document generates approximately 25,000 lines. Using individual heap objects for every glyph/cluster would exhaust memory and trigger catastrophic garbage collection thrashing.
Instead, we reuse the packed flat numeric arrays (`Float64Array`) from Phase 4 (`PackedShapedRun`). We allocate a single flat view that slices the original text engine's array without copying it.

## Consequences

- **Memory Efficiency:** Our empirical memory measurements confirm that 25,000 lines represented this way fit within ~12MB of RSS, providing plenty of headroom.
- **Sub-microsecond Queries:** Binary-searching flat arrays (mapping logical offset to visual coordinates) takes sub-microsecond time.
- **Strict Direction Handling:** Code handling line layout and hit testing must be careful. While spatial coordinates proceed monotonically left-to-right, navigating logical offsets requires reading the direction of the segment.
- **O(1) Memory Views:** Slicing lines relies on array views, strictly avoiding allocations in hot paths.
